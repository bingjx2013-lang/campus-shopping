# 服务端认证与资源授权差距审查 v1

## 本轮检查结果

### 已确认的现状

- 当前 API 路由仅发现健康检查 `GET /api/health` 和商品列表占位 `GET /api/v1/products`。
- 商品列表路由只校验分页参数，明确不连接数据库并返回空列表；目前没有用户/商户私有数据读取。
- 当前代码树中未发现登录、注册、短信验证码、会话刷新/撤销、登出、用户资料、商户管理、订单、钱包或文件访问 API。
- `src/features/auth/permissions.ts` 是纯角色权限映射函数，不负责认证身份、加载可信角色、资源归属判断或拒绝未登录请求。
- `instrumentation.ts` 负责生产环境密钥启动检查；它不是请求认证或 API 授权中间件。
- 财务角色同时拥有申请与批准权限，但 `canApproveFinancialAdjustment` 检查申请人与审批人必须是不同用户。该检查只有在服务端使用可信会话用户 ID、并在资金写入事务中强制执行时才有效。
- `validateTwoPersonApproval` 的领域函数覆盖两名不同审批人、申请人不得自批、审批阶段唯一和同一申请约束；它本身不持久化审批记录，也不保证并发请求下的数据库原子性。

## 风险结论

目前没有发现可利用的跨用户数据读取接口；更准确地说，当前业务 API 尚未实现，因而不能把“没有发现越权”表述为“已通过完整越权测试”。

当前最大风险是未来业务接口上线时误把客户端传入的 userId、merchantId 或 role 当作可信身份，或只在页面隐藏按钮而没有服务端鉴权。所有私有业务接口必须先认证，再执行资源级授权。

## 下一阶段实施要求（上线阻断项）

1. 建立服务端唯一认证入口：会话必须由服务端验证签名、有效期、撤销状态和设备状态；客户端提交的角色/用户 ID 不得作为身份依据。
2. 每个 API / Server Action 明确匿名或登录要求；默认拒绝，只有健康检查和明确公开的商品目录等接口可匿名访问。
3. 每次读写订单、地址、聊天、文件、钱包和商户数据时，按数据库中的真实 owner / merchant membership 做资源级授权，不能只判断“已登录”或角色。
4. 管理员权限在服务端重新从可信账户/角色记录读取；敏感操作检查权限、操作者 ID、目标资源、原因和审计记录。
5. 财务调整必须由不同用户申请与批准；两阶段审批须在数据库事务中锁定申请，校验两个不同审批人及申请人隔离，只有两阶段均批准后才能执行资金分录。
6. 验证码按手机号、用途绑定，限时、限尝试、限发送频率并原子消费；不得明文记录或重复使用。
7. 会话刷新令牌轮换、旧令牌重放检测、单设备/全设备撤销和新设备验证必须有服务端实现及测试。
8. 文件访问使用短时授权或受控下载接口；校验文件所有者、会话和业务关系，不能只凭猜测 URL 访问。
9. 增加端到端拒绝测试：未登录、过期/撤销会话、用户 A 访问用户 B 资源、商户 A 访问商户 B 订单、普通用户访问管理员接口、错误管理员角色、审批人自批、重复回调/重放。
10. 对库存、订单、退款、钱包、结算和提现的资金/状态写入采用数据库事务、幂等键和并发测试。
