# 校园购跨模块集成契约 v1.0

> 配套需求：docs/requirements/校园购完整需求基准_v1.0.md
> 目的：七条工作线共享同一组技术边界，减少并行开发冲突。
> 状态：实现前契约草案；所有金额均使用人民币 CNY，服务端为最终可信来源。

## 1. 全局技术约定

- 主键：UUID；面向用户展示的订单号、商家号等使用独立生成的业务编号，不暴露数据库自增序号。
- 时间：数据库使用 timestamptz，服务端统一存 UTC；展示时按学校配置时区转换。
- 金额：PostgreSQL numeric，不使用浮点数；API 金额使用十进制字符串，例如 "12.30"。
- 数量：库存使用 bigint；订单购买数量使用正整数并设合理上限。
- API：统一前缀 /api/v1；所有写请求服务端鉴权、授权、校验、幂等和审计。
- 响应：成功和失败均返回统一 envelope；失败包含稳定 error.code、可读 message、requestId；不向客户端泄露堆栈、SQL 或内部凭证。
- 分页：page 从 1 开始，pageSize 默认 20，最大 50；列表响应包含 items 与 pagination。
- 删除：订单、财务、审核和库存流水不物理删除；商品等可运营对象采用软删除/状态归档。
- 权限：默认拒绝；客户端角色标识不能作为授权依据；每次请求从可信会话解析用户与权限。
- 幂等：订单创建、支付、库存预留/释放、退款、钱包充值/提现、结算和财务调整必须要求 Idempotency-Key，并在服务端按业务主体和操作范围唯一约束。

## 2. 核心领域对象边界

| 领域 | 核心对象 | 权威数据归属 |
|---|---|---|
| 身份 | User、StudentProfile、GuardianLink、Session、VerificationCode | Auth/Identity |
| 权限 | Role、Permission、RoleGrant、ApprovalRequest | Access Control |
| 商家 | Merchant、MerchantMember、MerchantPolicy、MerchantAgreement | Merchant |
| 商品 | Category、Product、ProductOption、SKU、ProductMedia | Catalog |
| 库存 | InventoryBalance、InventoryMovement、InventoryReservation | Inventory |
| 订单 | Order、MerchantOrder、OrderItem、OrderStatusHistory | Order |
| 配送 | Shipment、ShipmentItem、Pickup/Delivery details | Fulfillment |
| 资金 | Wallet、WalletTransaction、JournalEntry、JournalLine | Finance |
| 售后 | AfterSalesCase、Refund、RefundFreezeAllocation | After-sales |
| 结算 | SettlementBatch、SettlementItem、SettlementHold、MerchantReceivable、Withdrawal | Settlement |
| 互动 | Conversation、Message、Review、Favorite、Notification | Social |

禁止不同工作线各自创建同义但不兼容的用户、商家、订单、钱包或状态字段。新增对象必须在本契约中登记其唯一数据所有者。

## 3. API 领域边界（建议首批接口）

### 身份与权限
- POST /api/v1/auth/register
- POST /api/v1/auth/login
- POST /api/v1/auth/verify-code
- POST /api/v1/auth/refresh
- POST /api/v1/auth/logout
- GET /api/v1/me
- GET /api/v1/me/permissions

验证码不得明文存储；有效期 2 分钟；发送、校验、登录均需限流；刷新会话应轮换 refresh token，旧 token 立即失效。

### 商品与库存
- GET /api/v1/products
- GET /api/v1/products/{productId}
- POST /api/v1/merchant/products
- PATCH /api/v1/merchant/products/{productId}
- POST /api/v1/merchant/products/{productId}/skus
- POST /api/v1/merchant/skus/{skuId}/inventory-adjustments

库存调整只能走专用命令接口并生成流水；不能允许客户端直接 PATCH stock 数值。

### 购物车与订单
- GET /api/v1/cart
- PUT /api/v1/cart/items/{skuId}
- DELETE /api/v1/cart/items/{skuId}
- POST /api/v1/orders/preview
- POST /api/v1/orders
- GET /api/v1/orders/{orderId}
- POST /api/v1/orders/{orderId}/cancel
- POST /api/v1/merchant/orders/{merchantOrderId}/shipments

订单预览不锁定价格或库存；正式下单时服务端重新校验商品状态、价格、促销、配送费、库存并建立预留。主订单和商家子订单在同一业务事务中创建。

### 钱包、支付、退款和结算
- GET /api/v1/wallet
- GET /api/v1/wallet/transactions
- POST /api/v1/wallet/topups
- POST /api/v1/orders/{orderId}/wallet-payments
- POST /api/v1/aftersales
- POST /api/v1/aftersales/{caseId}/merchant-decision
- POST /api/v1/aftersales/{caseId}/platform-intervention
- POST /api/v1/merchant/settlements
- POST /api/v1/merchant/withdrawals

客户端只能发起业务意图；不能指定钱包最终余额、账务分录、结算净额或退款实际完成状态。账本写入由服务端领域服务在事务内完成。

## 4. 订单与库存状态约定

### Order（主订单）
- pending_payment
- paid
- partially_fulfilled
- fulfilled
- completed
- cancellation_pending
- cancelled
- aftersales_pending

### MerchantOrder（商家子订单）
- pending
- accepted
- awaiting_stock_decision
- preparing
- partially_shipped
- shipped
- delivered
- completed
- aftersales_pending
- cancelled

### InventoryReservation
- reserved：已预留，尚未最终扣减/释放
- committed：订单确认后按库存策略完成扣减
- released：订单取消或预留超时释放
- expired：超时任务已标记失效

下单预留必须在 SKU 维度原子执行；tracked 库存禁止超卖；unlimited SKU 不做数量扣减但仍记录销售流水。取消、支付失败、超时释放均需幂等。多次发货时，累计发货数量不得超过订单商品数量。

## 5. 资金状态与账本规则

- 订单支付：买家钱包扣款、商家待结算负债/应付款、平台费用等分录必须在同一资金事务内形成平衡分录。
- 退款申请不等于退款完成；批准时先冻结对应商家未结算款，完成退款时消耗冻结分配并生成冲正/退款分录。
- 商家待结算款不足：冻结可用部分，差额登记 merchant_receivable，暂停该商家相关结算，禁止负余额静默穿透。
- 商家结算：从待结算余额转入商家校园钱包；微信提现是独立提现流程，不得与订单支付混为一体。
- 每个已过账 journal entry 不可修改或删除；差错通过反向分录纠正。
- 每个 journal entry 借方总额必须等于贷方总额且大于零。
- 同一业务事件的账务入账必须幂等；重复回调、重试和并发请求不得重复扣款或重复退款。
- 资金金额的舍入、优惠分摊、佣金计算必须统一采用 decimal 规则并保留计算快照。

## 6. 安全和审计约定

- 每个资源操作都校验 owner/merchant membership/permission，避免 IDOR。
- 管理员敏感操作要求原因、审批状态和审计记录；财务高风险操作双人审批。
- 日志记录 requestId、actorId、action、resource、结果和时间；禁止记录密码、验证码、完整 token、支付密钥。
- 上传文件采用私有对象存储键；下载必须经过鉴权或短时签名 URL；校验 MIME、大小、扩展名和恶意内容。
- 所有外部回调验签、校验时间窗并幂等处理；回调不可直接信任客户端传来的状态。
- 关键领域事件通过事务发件箱写入；消费者至少一次投递并以 event_key 去重。

## 7. 数据库草案审查清单（迁移执行前必须完成）

以下为当前 0002/0003 草案需要补齐或验证的事项，不代表已经修复：

1. 身份关系：student_profiles 目前只有单个 guardian_user_id；需求允许监护人关系更复杂，应采用独立 guardian_student_links，并明确主监护人、关系类型、有效期和验证状态。
2. 钱包归属：wallets.owner_type + owner_id 是多态引用，数据库无法直接保证目标存在；必须由受限服务层/触发器策略保证，或拆分明确的 owner 关联表。
3. 订单金额：orders 与 merchant_orders 需要定义优惠分摊、运费、平台费用、应付金额的恒等式与舍入规则，并增加数据库约束/服务层不变量测试。
4. 订单快照：order_items 应保留商品标题、SKU 规格、商家名称、原价/成交价、优惠分摊、税费（如适用）等完整快照。
5. 库存并发：reservation 表必须与条件更新/行锁策略结合；仅有 reservation 表和索引不能防止超卖。
6. 退款分配：同一退款可能涉及多商家/多子订单，分配总额必须等于批准退款额；不足额必须形成应收并阻止相关结算。
7. 账本：需要验证并发过账时的账户级锁/序列化策略、分录来源唯一性、反向分录规则和服务角色权限。
8. 审批：双人审批必须保证申请人不能审批自己，两个审批人不能是同一主体；不能只依赖 UI。
9. 会话与验证码：增加目的、主体、尝试次数、发送频率、消费原子性、设备变更和会话轮换测试。
10. 文件/消息：需要对象存储生命周期、访问授权、病毒扫描、消息成员权限、举报和内容审核流程。
11. 迁移安全：extension、schema、search_path、权限/grant、回滚/前向修复方案必须在隔离 PostgreSQL 15 环境验证。
12. 学校配置：保持单校边界；school_config 仅为明德学校内部配置，不设计 school_id 贯穿所有表的多租户机制。

## 8. 并行开发交付标准

每条工作线必须提交：
- 领域模型与迁移草案（不执行生产迁移）
- API 契约及权限矩阵
- 正常、异常、并发、重复请求测试
- 审计事件与日志字段
- 与相邻工作线的集成测试
- CI 结果与未解决风险清单

## 9. 当前不允许自动执行的操作

未获得用户单独明确授权前，不执行真实数据库迁移、不接入真实充值/提现/支付、不改生产服务、不处理真实用户资金、不把草案 SQL 当作已验证方案。
