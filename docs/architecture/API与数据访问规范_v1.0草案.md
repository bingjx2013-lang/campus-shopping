# 校园购 API 与数据访问规范 v1.0（草案）

## 1. 通用约定
- API 前缀建议：/api/v1。
- JSON 请求/响应使用 UTF-8；时间戳统一存 UTC，界面按用户时区显示。
- 金额字段使用整数最小单位并明确 currency，或使用固定精度 NUMERIC；不得使用浮点数。
- 每个响应包含稳定的业务错误码、可读 message 和 request_id；不得向客户端泄露 SQL、堆栈或密钥。
- 所有写操作由服务端校验身份、角色、资源归属和业务状态。

## 2. 身份与权限
- 默认拒绝，按最小权限授权。
- 买家只能访问本人订单、钱包和售后；监护人访问范围必须由已验证的监护关系决定。
- 商家只能访问所属店铺及其订单、商品、库存和结算数据。
- 平台后台按岗位拆分权限，财务、客服、审核、安全管理员不得默认互相拥有全部权限。
- 高风险操作要求重新验证身份；大额资金调整和异常退款执行双人审核。

## 3. 幂等性
- 下单、支付回调、取消、退款申请/处理、库存预占/释放、结算和提现等写操作必须支持幂等。
- 客户端为可重试写请求提供 Idempotency-Key；服务端在数据库中持久化作用域、请求摘要、处理状态和结果。
- 同一幂等键不同请求内容必须拒绝，不能复用旧结果。
- 第三方回调需验证签名，并以提供方事件 ID 建立唯一约束。

## 4. 事务边界
- 订单创建、订单项快照、库存预占、库存流水、幂等结果和 outbox 事件应在同一数据库事务中提交。
- 钱包余额变化与账务分录、业务单据状态变化在同一事务中完成。
- 外部支付/短信/邮件/对象存储调用不得持有数据库长事务；采用 outbox/inbox 或可恢复状态机。
- 多 SKU 操作按 SKU ID 稳定排序后加锁；所有涉及订单、预占、SKU 的流程遵循同一锁顺序。
- 事务失败应整体回滚；死锁/序列化失败只对明确可重试错误进行有限次数重试。

## 5. 建议接口域
- /auth：登录、登出、会话、验证码、新设备验证
- /users：个人资料、班级信息、监护关系
- /stores：店铺资料、资质、经营状态
- /products、/skus：商品、规格、上下架
- /inventory：库存查询、入库、预占、释放
- /carts：购物车
- /orders：总单、店铺子单、订单状态
- /wallet：余额、充值/提现申请、流水
- /payments：支付发起、支付结果通知
- /refunds：退款、售后、平台介入
- /shipments：分批发货、物流、签收
- /settlements：结算单、冻结、商家提现
- /admin：审核、风控、配置、审计

## 6. 状态与审计
- 状态迁移必须由服务端业务命令执行，不允许客户端直接提交目标状态。
- 对状态迁移记录操作者、角色、前后状态、原因、时间、request_id。
- 财务流水采用追加式记录；错误通过冲销/调整单修正，不直接覆盖历史记录。
- 所有分页、筛选和导出接口必须执行资源范围授权，避免越权查询。

## 7. 文件上传
- 服务端校验文件大小、扩展名、真实 MIME、文件签名；随机化存储键。
- 默认私有存储；下载使用短期授权 URL。
- 图片处理、恶意文件扫描和上传频率限制在上线前落实。
