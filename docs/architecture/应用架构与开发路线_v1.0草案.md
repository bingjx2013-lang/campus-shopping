# 校园购应用架构与开发路线 v1.0（草案）

## 1. 项目边界
- 服务对象：明德中英文学校校内用户，永久单校；不设计多学校租户隔离或多校运营。
- 学校、班级、学籍字段仅用于校内身份与运营管理。
- 本文是开发架构草案，不代表已有前后端程序、云资源或线上服务。

## 2. 建议的逻辑分层
1. Web/PWA 前端：学生/家长买家端、商家端、平台运营后台；按角色呈现功能。
2. 应用 API：身份与权限、商品/SKU、库存预占、购物车/订单、支付钱包、退款售后、发货、结算、通知。
3. PostgreSQL：业务数据、约束、事务、账务分录、审计记录。
4. 异步任务：订单超时、支付结果核验、通知、退款/结算对账、outbox 消费。
5. 对象存储：商品图片、聊天/售后附件等；私有文件使用短期签名访问。

## 3. 技术选型建议（待确认）
- 前端：TypeScript + React/Next.js，优先移动端响应式/PWA。
- API：TypeScript 服务端（Next.js Route Handlers 或独立 Node.js API）；在明确部署方式前不锁定框架。
- 数据库：PostgreSQL；Supabase 可作为候选托管平台，但当前账号尚未创建校园购项目。
- 文件：私有对象存储；Supabase Storage 或兼容 S3 的方案需比较后确定。
- 部署：Render 可承载 Web/API/Worker；Cloudflare 可提供 DNS/CDN/WAF。均需单独确认后配置。

## 4. 关键业务模块
- 校内账号、监护关系、角色与权限
- 店铺与商家资质、商品、SKU、独立库存
- 购物车、总单/店铺子单、订单快照
- 校园钱包、支付流水、双重记账
- 退款、售后介入、结算冻结与商家提现
- 分批发货、物流、收货
- 平台后台、审计、风控、运营配置

## 5. 关键一致性原则
- 价格、商品名称、SKU 规格等在下单时写入订单快照。
- 有限库存必须在数据库事务内锁定 SKU、原子检查并预占；不得只依赖前端库存显示。
- 支付、取消、过期任务竞争时必须使用统一锁顺序和状态机，保证只有一个终态操作成功。
- 钱包和账务变动必须由服务端受控事务产生不可随意改写的流水；禁止后台直接改余额。
- 退款、冻结、结算必须具备幂等键、审计记录和可追溯关联。
- 所有金额使用最小货币单位整数或明确精度的 NUMERIC，禁止浮点数金额运算。

## 6. 开发阶段
1. 固化数据库设计与迁移基线，完成隔离数据库验证。
2. 建立账号、会话、角色权限和审计基础。
3. 建立商品/SKU/库存及并发预占服务。
4. 建立购物车、订单、钱包与支付账务流程。
5. 建立退款、售后、分批发货和结算流程。
6. 建立后台、通知、监控、备份与恢复演练。
7. 完成安全测试、并发测试和验收后再讨论生产发布。

## 7. 发布原则
- 开发、测试、生产环境必须隔离，凭据不得跨环境复用。
- 任何数据库迁移先在隔离测试库验证并备份；禁止直接对生产执行草案 SQL。
- 生产发布必须经过代码审查、自动化测试、回滚预案和明确授权。
- 本阶段仅建立 Git 文档，不创建 Supabase 项目、不更改 Cloudflare、不创建/修改 Render 服务、不部署。
