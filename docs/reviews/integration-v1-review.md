- PR #3 同时新增 `sku-domain.ts` 与 `sku.ts`，两套库存函数接口不同。
- PR #4 同时新增 `calculation.ts` 与 `order-domain.ts`，状态名和订单计算接口不同。
- PR #5 同时新增 `ledger.ts` 与 `ledger-domain.ts`，金额字段及校验接口不同。
- PR #6 同时新增 `approvals.ts` 与 `approval-domain.ts`，审批数量规则不一致：一个可配置，另一个固定恰好两人。
- PR #7 的 `security-config.ts` 只是环境校验函数，当前未看到启动流程或 API 中调用它；不能视为 AUTH_SECRET 已在运行时被强制校验。
- PR #8 只集成各领域的一部分文件。不要按 #2–#8 当前顺序直接全部合并；先确定唯一规范模块，再把其余模块改为兼容适配或删除重复实现。

建议整合顺序：先确定统一权限/角色定义；再确定 SKU/库存接口；再统一订单行计算与父订单/商户子订单状态；再统一账务分录及审批模型；最后整合安全配置和 CI。完成后只保留一个集成 PR 进入主分支。

## 数据库草案阻塞项（不得直接上线）
以下结构性问题已经在独立的草稿 PR #10 中提出修订，但尚未经过 PostgreSQL 实际迁移验证，因此只能视为设计层改进，不能视为生产问题已经关闭：
1. 钱包多态 owner 已改为 user / merchant / platform 互斥列和外键约束。
2. 单一 `guardian_user_id` 已改为学生—监护人关系表，记录关系类型、验证时间、主要监护人和有效期。
3. 会计分录已改用业务事件类型与唯一幂等键，允许同一订单发生不同资金事件。
4. 增加商户身份核验引用和协议签署证据表，保存签署人、协议版本、内容哈希、时间和证据引用。
5. 学校配置已增加单校单例限制，父订单增加金额算式 CHECK。

仍然阻塞上线的事项：
6. `journal_lines` 及资金表使用 numeric 金额，应用域使用整数分；需要统一货币精度、舍入规则与入库映射，避免双重转换。
7. 订单父子金额、订单行折扣分摊、发货累计数量、累计退款上限等跨行不变量不能靠现有 CHECK 单独保证，需要事务服务/约束触发器和并发测试。
8. 库存预留表本身不防超卖；必须用行锁或带库存条件的原子 UPDATE，在同一事务里完成预留、支付确认、释放和幂等处理。
9. 退款冻结、结算暂停、商户应收款必须在事务内串行化并具备幂等键；需模拟退款与结算并发、余额不足和重复回调。
10. 验证码需要原子消费、用途绑定、有效期/尝试次数/发送频率约束；会话需验证刷新轮换、撤销和设备变更流程。
11. 商户签署应用服务必须校验 signer 为有效 owner/operator，且身份核验已通过、未过期；数据库结构本身不能代替授权逻辑。
