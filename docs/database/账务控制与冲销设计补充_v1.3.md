# PostgreSQL 账务控制与冲销设计补充 v1.3

> 本文件是设计约束和静态审查结果，不是已验证的数据库实现。没有执行 SQL，也没有连接数据库。

## 本轮新增：冲销关系字段

`journal_entries` 增加 `reversal_of_entry_id`，自引用原分录，并增加：
- 禁止分录引用自身；
- 部分唯一索引，限制一个原分录最多存在一条直接冲销分录；
- 冲销分录仍必须遵循 draft -> posted 流程；过账后不可修改或删除。

该字段只建立冲销关联，**不自动证明冲销金额正确**。受控 posting 服务必须在同一事务内锁定原分录及冲销分录，并验证：
1. 原分录已经 posted，且不是已被冲销的无效对象；
2. 冲销分录按账户、钱包、币种维度逐项反转原分录借贷方向和金额；
3. 原分录尚未有冲销记录；并发请求通过唯一索引保证只有一个成功；
4. 冲销分录与原分录的业务来源、操作人、原因、时间均写入不可篡改审计记录；
5. 冲销分录过账后，原分录和冲销分录都保持不可变。

## 受控过账 API 设计要求（尚未实现）

建议应用不得直接写入 `journal_entries.status='posted'`。应实现专用事务函数/服务，执行：
1. 验证调用者具备对应账务动作权限；
2. 对 entry 行执行 `SELECT ... FOR UPDATE`，避免同一 entry 并发过账；
3. 校验 entry 当前为 draft、存在明细、借贷总额非零且相等；
4. 若为冲销分录，校验原分录状态、冲销唯一性和逐账户反向金额；
5. 写入审计事件，再将状态改为 posted；
6. 全部步骤在一个数据库事务内提交；失败则整体回滚。

生产权限建议：
- 业务运行角色对账本表仅授予必要 SELECT 和创建 draft 的权限；
- 撤销业务角色对已过账分录/明细直接 UPDATE、DELETE 权限；
- 仅专用 posting 服务角色可执行过账；
- 迁移 owner、posting owner、业务运行角色分离；函数如采用 SECURITY DEFINER，必须固定安全的 search_path、限定 EXECUTE 权限，并对对象使用 schema-qualified 名称；
- 不允许应用使用超级用户或表 owner 凭据。

## 尚未完成的安全边界

- 当前 SQL 仅有冲销关联字段和唯一索引，尚无专用 posting 函数、角色/授权脚本、冲销金额核验触发器或完整审计流水。
- 不能把“有 reversal_of_entry_id”视为冲销流程已经安全可用。
- 当前余额触发器属于防线，不足以替代受控过账 API 和并发锁。
- 需要确认业务是否允许冲销本身再冲销；本设计建议采用新更正分录引用原始分录，避免无限链条，特殊情况由财务审批流程处理。

## 验收用例

1. 同一原分录并发创建两条冲销记录，最多一条成功。
2. 冲销未过账原分录、已冲销分录或不存在的分录必须失败。
3. 冲销分录借贷方向未逐账户反转、金额不一致时必须失败。
4. 非 posting 角色尝试过账、修改或删除已过账分录必须失败。
5. posting 过程中任何步骤失败，状态和审计记录不得部分提交。
6. 原分录和冲销分录过账后均不可修改、删除。
7. 所有测试需在隔离 PostgreSQL 环境执行并保存版本、SQL、退出码和结果；当前尚未执行。
