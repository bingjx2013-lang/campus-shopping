# 库存并发与超卖控制补充 v1.4

> 状态：设计与静态审查稿。本文不代表库存服务已实现。当前 0002/0003 均未在 PostgreSQL 执行；本轮不连接数据库、不运行迁移或并发测试。

## 1. 审查结论

现有结构：
- `skus.stock_mode`：`tracked/unlimited`。
- `skus.stock_on_hand`：非负库存数量。
- `inventory_movements`：库存变动流水。
- `inventory_reservations`：预占、消费、释放、过期状态及幂等键。

主要缺口：
1. 预占记录插入并不自动扣减 SKU 库存；仅有表和索引无法防止两个并发请求同时读到相同库存。
2. 没有定义预占/消费/释放的唯一合法状态迁移，也没有保证同一预占只能结算一次的事务服务。
3. 没有规定订单创建、订单项快照、预占、库存流水和请求幂等记录必须同事务提交。
4. 支付成功与预占超时任务可能竞争；若先检查状态后更新而未锁定同一预占行，可能出现重复释放或已付款订单被释放库存。
5. 多 SKU 订单若按不同顺序加锁，可能死锁。
6. `inventory_reservations.order_item_id` 可空，且当前没有约束确保预占数量与订单项数量对应；部分发货也不能直接当作库存消费。

## 2. 库存数量的唯一口径

对于 `stock_mode='tracked'`：
- `stock_on_hand` 表示当前可用库存，不包含已预占数量。
- 创建预占时在同一事务内减少 `stock_on_hand`。
- 预占成功后，库存视为已从可用库存中隔离；支付成功将预占标记为 `consumed`，不再次减少 SKU 库存。
- 订单取消或预占超时且确认订单仍未支付时，将预占标记为 `released` 或 `expired`，并在同一事务内将数量加回 `stock_on_hand`。
- 退款成功不自动恢复库存。商品经商家确认可再次销售后，走独立补货/入库事务。

对于 `stock_mode='unlimited'`：
- 下单不因 `stock_on_hand` 数量不足而拒绝，也不对该字段做预占扣减或释放加回。
- 仍然创建预占记录用于订单生命周期、幂等和支付/取消竞争控制；消费/释放只改变预占状态，不产生有限库存数量变动。
- 不得把 unlimited SKU 的数量字段当成实际库存展示或扣减依据。

任何库存数量变化都必须在同一事务内写入 `inventory_movements`。建议流水类型明确枚举：`restock`、`reserve`、`release`、`adjustment`、`return_restock`。`reserve` 为负数，`release/restock/return_restock` 为正数；unlimited 的预占/释放不写数量变动流水。

## 3. 下单预占：事务和锁顺序

应用服务必须为一次下单请求生成稳定的请求幂等键，并在事务内执行：

1. 先检查订单请求幂等记录；同一买家、同一业务操作的重试必须返回原订单结果，不能创建第二张订单。
2. 校验商品可售、SKU 有效、数量为正、价格快照与订单金额计算一致。
3. 将订单涉及的 SKU ID 去重并按 UUID 升序排序，按固定顺序逐个锁定 SKU 行（`SELECT ... FOR UPDATE`）。所有库存服务统一使用同一锁顺序。
4. 对每个 tracked SKU，在持有行锁时检查可用库存足够，并执行条件更新：`UPDATE skus SET stock_on_hand = stock_on_hand - :qty WHERE id=:sku_id AND stock_mode='tracked' AND stock_on_hand >= :qty RETURNING stock_on_hand`。没有返回行即库存不足，整个事务回滚。
5. 创建订单、店铺子单、订单项快照和预占记录；为每条预占写入稳定且唯一的预占幂等键。
6. 对 tracked SKU 写入对应负数 `inventory_movements`，引用订单/预占。
7. 写入请求幂等结果及必要的 outbox 事件。
8. 全部成功后提交；任何一步失败都整体回滚，不能留下扣库存无订单、订单无预占或无流水的半成品。

并发结果：同一 SKU 的请求会在 SKU 行锁上串行化；后续请求读取前一事务提交后的库存，并由条件更新再次保护非负库存。禁止使用“先普通 SELECT 读库存，再无锁 UPDATE”的方式。

## 4. 支付、取消、过期：统一锁定顺序和状态机

所有终结预占的操作必须先锁定相关订单/支付状态，再按固定顺序锁定该订单的预占行，最后锁定涉及 SKU 行。系统内所有相关事务必须遵守一致的全局锁顺序，避免一个流程先锁 SKU、另一个流程先锁 reservation 造成死锁。

### 支付成功
- 在一个事务内锁定订单并确认订单仍处于允许支付的状态。
- 锁定该订单所有 reservation。
- 仅允许 `reserved -> consumed`；若全部预占已经释放/过期，禁止将订单标记为支付成功，转入支付异常/人工对账处理。
- 将预占改为 consumed 并写 resolved_at；不再次扣减 stock_on_hand。
- 同一事务记录支付结果、钱包流水/账务分录和 outbox 事件；支付渠道重复回调由支付幂等键保证只处理一次。
- 支付与超时释放必须通过同一订单锁和预占行锁竞争，不能各自独立检查后操作。

### 取消订单
- 锁订单并确认尚未支付且状态允许取消。
- 锁定所有仍为 reserved 的预占。
- 对 tracked SKU 在同事务中加回数量，预占状态更新为 released，写正数 release 流水。
- 已 consumed 的预占不能释放；已 released/expired 的预占不得再次加回库存。
- 订单状态历史、库存变动和订单状态必须同事务提交。

### 超时过期任务
- 任务只负责找候选记录；候选查询不代表已获得释放权。
- 对候选订单逐个锁订单，再锁该订单预占；重新检查订单支付状态、reservation 当前状态和 expires_at。
- 只有订单仍未支付且预占仍为 reserved、且已到期时，才允许 `reserved -> expired` 并加回 tracked SKU 库存。
- 使用 `FOR UPDATE SKIP LOCKED` 可让多个过期 worker 分批领取候选项，但仍必须在锁内重新检查条件。
- 如果支付事务先获得订单锁并完成消费，过期 worker 必须看到 consumed 并跳过；如果过期事务先完成释放，支付流程必须拒绝按正常路径确认支付并进入异常处理。不得让已释放库存的订单照常支付成功。

## 5. 状态迁移规则

| 当前状态 | 操作 | 允许结果 | 库存数量 |
|---|---|---|---|
| reserved | 支付成功 | consumed | 不变 |
| reserved | 买家取消 | released | tracked 加回 |
| reserved | 到期且订单未支付 | expired | tracked 加回 |
| consumed | 取消/过期任务 | 拒绝 | 不变 |
| released | 重复取消/释放 | 幂等返回，不再处理 | 不变 |
| expired | 重复过期任务 | 幂等返回，不再处理 | 不变 |
| released/expired | 支付成功 | 拒绝正常支付确认，转异常处理 | 不变 |

状态更新必须使用条件更新或锁内检查，例如仅在 `WHERE status='reserved'` 时更新；更新行数不是 1 时不得执行库存加回。单纯使用 CHECK 约束不能实现跨表状态机。

## 6. 幂等和唯一性要求

- 下单请求：按买家/业务范围保存稳定请求幂等键及结果；同键不同请求内容必须拒绝，不能静默复用。
- 预占：现有 `idempotency_key UNIQUE NOT NULL` 保留；键应由业务请求稳定生成，同一预占重试复用。
- 支付：使用支付尝试/渠道回调稳定幂等键。
- 释放：以 reservation ID + 终结动作作为稳定业务键；只有状态仍为 reserved 的事务能加回库存。
- 库存流水：建议增加业务事件唯一键（例如 reservation_id + movement_type 的唯一约束或独立 event_key），防止服务重试重复写流水。实施前需先确定补货、人工调整等流水的唯一键语义。
- 不可仅依赖随机 reservation UUID 作为请求幂等：请求重试若生成新 UUID，仍会重复预占。

## 7. 多 SKU、部分发货和售后边界

- 多 SKU 下单必须先按 SKU ID 排序锁行，再执行库存校验和预占。
- 部分发货是订单履约数量，不是再次扣减可用库存；预占在支付成功时已消费。发货累计数量必须另行约束不超过订单项数量。
- 退款成功不自动补库存；退货入库需有验货/可销售确认及独立入库流水。
- 商家缺货、订单取消、支付失败等场景必须调用同一个释放服务，禁止各业务入口自行执行库存加法。
- 订单项删除/改量不应直接改已创建预占；按现有规则买家下单后不能直接改数量，取消后重新下单。

## 8. 建议的实现接口（应用服务/数据库函数）

建议封装为受控事务接口，而不是让普通业务代码直接写 `skus.stock_on_hand`：
- `create_order_and_reserve_stock(request_key, items...)`
- `consume_order_reservations_on_payment(order_id, payment_key)`
- `release_order_reservations(order_id, reason, request_key)`
- `expire_order_reservations(order_id)`
- `restock_sku(sku_id, quantity, reason, actor_id, event_key)`

接口内部必须执行上述锁顺序、状态校验、幂等、流水及审计。应用数据库角色应撤销对库存数量和预占状态的任意直接写权限，仅授予受控函数/服务所需权限。具体 GRANT/REVOKE、函数签名和安全 search_path 需结合实际部署角色再设计。

## 10. 隔离数据库验收用例

1. tracked SKU 库存为 5，两个会话同时各买 4：最多一个成功，库存不为负数。
2. 同一请求幂等键并发重试：只产生一张订单、一组预占和一组库存流水。
3. 两个订单同时购买多个相同 SKU、但传入顺序相反：服务统一排序加锁，验证不会形成持续死锁；发生死锁时整笔事务可安全重试。
4. 预占后支付成功：状态变 consumed，库存不再次减少。
5. 预占后取消：只加回一次；重复取消不增加第二次。
6. 过期 worker 与支付回调并发：最终只能是 consumed 或 expired/released 之一；不能同时消费和释放。
7. 过期任务重复执行或多个 worker 同时执行：库存只加回一次。
8. unlimited SKU 即使 stock_on_hand 为 0 也可下单，且不修改库存数量。
9. 事务在扣库存后、写订单项前故意失败：回滚后库存、订单、预占、流水均无残留。
10. 退款成功不自动加库存；只有独立验货补货流程才增加库存和流水。
11. 任何直接把 stock_on_hand 更新为负数的操作必须失败；普通业务角色不能绕过受控库存接口。
12. 验证库存流水与库存数量变更逐笔可追溯、可对账。
